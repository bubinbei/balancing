# G14 — проверяемая поставка и передача на аудит

**Результат:** воспроизводимый реализованный комплект с доказательствами и границами; обе площадки содержат одну ревизию; владелец получает готовый запрос независимому аудитору. Этот этап выполняет младшая модель после реализации. Первичная публикация плана относится к P00.

**Читать:** [README](../README.md), [STATE](../STATE.md), эту карточку, [AUDIT_HANDOFF](../docs/AUDIT_HANDOFF.md), [PUBLISHING](../docs/PUBLISHING.md), итоговые отчёты G12/G13. Прочие отчёты открывать точечно по сводке.

**Файлы:** будущие `evidence/reports/G14.md`, `evidence/reports/AUDIT_PACKAGE.md`, `docs/OPERATING_GUIDE.md`, манифест релиза и изменения README/STATE/RECENT. Чертежи/исходники сохраняют собственные ревизии.

## Срезы

1. Сверить все зависимости и отчёты: ни один физический pass не основан только на build/synthetic. Составить таблицу «требование → файл реализации → тест → доказательство → ограничение». Отрицательный результат по целевой чувствительности записать на первом экране документации.
2. Из чистого отдельного каталога воспроизвести установку зависимостей, сборку firmware и тесты host по зафиксированным версиям. Не прошивать устройство как побочный эффект сборки. Сверить формат образа/загрузчик и сохранённые артефакты; если сборка недетерминированна, указать причину и проверяемые инварианты.
3. Составить короткое руководство оператора: соединения и версии, предзапусковые проверки, допустимые режимы, запись/остановка, калибровка, чтение качества, запрет коррекции при отказе модели, восстановление данных. Связать допуск скорости с конкретной механической ревизией.
4. Подготовить пакет AUDIT_HANDOFF: отчёты, манифесты, команды, синтетические fixtures и разрешённые обезличенные реальные примеры либо честная граница доступности сырых данных. Не включать секреты и большие личные записи по умолчанию.
5. Выполнить профильные проверки, docs check, просмотр индекса/истории и публикацию на GitHub/Gitea. Сверить HEAD обеих площадок и публичность. Передать владельцу ссылки, проверенную ревизию и запрос аудита; не объявлять независимый аудит уже проведённым.

## Приёмка

- `PASS`: вся реализация воспроизводима по инструкции с записанными ограничениями; обязательные предшественники действительно passed.
- `PASS`: аудитору понятны источники каждой заявленной характеристики, отрицательные результаты и границы hardware validation; доступные тесты запускаются без подключения стенда.
- `PASS`: оба remote содержат проверенную ревизию; Git diff/индекс чисты относительно поставки; частичная публикация не скрыта.
- `PASS`: пакет аудита не содержит секретов/чужих материалов, локальные записи защищены ignore; целевая точность не объявлена достигнутой, если G12 её не подтвердил.
- `FAIL`: отсутствующие физические проверки заменены текстом, реализация расходится с протоколом, отчёт относится к другой сборке или после проверок внесены непроверенные изменения.

**Откат:** сохранить предыдущую рабочую ревизию и исходные записи. Не force-push; исправление опубликованной ошибки — новый коммит с повторной затронутой проверкой.

**Доказательства:** отчёт G14, пакет аудита, версии инструментов/артефактов и результаты чистого воспроизведения. Проверенную финальную ревизию сообщить владельцу отдельно после последнего коммита.

**Завершение:** STATE сообщает «реализация готова к независимому аудиту» и реальные нерешённые ограничения. Следующий шаг — аудит владельцем, а не автоматическое расширение проекта.

Опубликуй проверенную ревизию по согласованным правилам и сверни контекст для аудитора. Не объявляй независимый аудит пройденным и не скрывай недостигнутую чувствительность.
