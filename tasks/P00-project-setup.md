# P00 — рабочий проект и публикация плана

**Результат:** самостоятельный репозиторий с проверяемой документацией и одной ревизией на двух площадках. Фактическое выполнение фиксируется в [отчёте P00](../evidence/reports/P00.md). Электроника, расчётный runtime и испытания сюда не входят.

**Читать:** [AGENTS](../AGENTS.md), [README](../README.md), [STATE](../STATE.md), эту карточку, [ROADMAP](../docs/ROADMAP.md), [PUBLISHING](../docs/PUBLISHING.md). Остальные документы — только по обнаруженной зависимости.

**Файлы:** будущий `tools/check_project.py`, при необходимости `tests/documentation/`, отчёт `evidence/reports/P00.md`; состояние, ссылки и настройки хранилища. Не изменять другие проекты и глобальные настройки Git.

## Срезы

1. Проверить существующее содержимое папки и сохранить его. Открыть корень как хранилище Obsidian либо проверить переносимые Markdown-ссылки и отметить, что визуальная проверка Obsidian пока не выполнена. Не устанавливать плагины без необходимости.
2. Реализовать минимальный локальный `tools/check_project.py` на стандартной библиотеке Python: ASCII-пути исходников; UTF-8; существование относительных Markdown-ссылок вне блоков кода; корректный JSON и XML схемы; STATE ≤2500 символов; уникальные ID карточек; существующие зависимости без циклов; согласованные статусы карточек/ROADMAP; для passed — отчёт и passed всех предшественников. Игнорировать `.git`, виртуальную среду, локальные измерения и кеши. Команда завершается ненулевым кодом и объясняет ошибку. Она не подтверждает физические доказательства автоматически.
3. Проверить checker на копиях/временных примерах: битая ссылка, неизвестный предшественник, цикл, ошибочный passed без отчёта. Не портить реальные документы ради теста. Выполнить успешную проверку самого плана.
4. Создать локальный Git-репозиторий с веткой main, только если собственного репозитория здесь ещё нет. До добавления файлов проверить ignore, происхождение, отсутствие секретов/измерений, diff и индекс. Не копировать историю соседнего проекта. Сохранить точный перечень добавленного.
5. По уже данному решению владельца создать публичные `balancing` на GitHub и Gitea, предварительно проверив владельца, адрес сервера и отсутствие конфликтующего репозитория. Использовать имеющийся штатный способ авторизации; не сохранять токены в проект. Опубликовать по PUBLISHING и сверить SHA/видимость обеих площадок. Если доступ отсутствует, завершить остальные срезы и явно оставить публикацию blocked; повторно не спрашивать разрешение на уже согласованную публичность.

## Приёмка

- `PASS`: checker проходит на реальном плане и отвергает перечисленные повреждённые примеры; все 16 карточек P00 и G00–G14 учтены.
- `PASS`: корень читается как хранилище с рабочими ссылками; известны границы проверки визуального отображения схемы и Mermaid.
- `PASS` публикации: HEAD, main GitHub и main Gitea совпадают, обе площадки подтверждают публичную видимость. Проверка датирована; токены не попали в отчёт. Доступность Gitea из Интернета не выводится из `private=false`.
- `FAIL`: созданы фиктивные аппаратные отчёты, скрыта частичная публикация, опубликованы локальные данные или переписана чужая история.

**Откат:** сохранять исходные документы и локальный коммит; не удалять существующие remote/репозитории и не force-push. Ошибки checker исправлять отдельным изменением, а не исключением реального нарушения из проверки.

**Доказательства:** `evidence/reports/P00.md`: команды checker/негативных примеров, просмотренные документы, URL площадок, проверенная ревизия и фактическая видимость. Итоговые SHA проверять после последнего коммита отчёта; для ссылки на этот коммит допустим `HEAD`, не создавать бесконечную цепочку коммитов ради вписывания собственного SHA.

**Завершение:** синхронно обновить карточку/ROADMAP/STATE/RECENT; перейти к G00 только после приёмки P00. Первичная публикация не означает прохождение G14.
