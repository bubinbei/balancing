Статус: **planned; реализация отсутствует**. Документ задаёт границы исполнения и критерии будущей проверки. Ни выбранная библиотека, ни успешная сборка не подтверждают точность времени, отсутствие потерь или пригодность механики.

## 1. Что делает контроллер

Контроллер сохраняет локальные сырые значения четырёх датчиков, отмечает время их готовности и время фронтов оптических каналов общим аппаратным таймером, передаёт записи в USB и сообщает качество. Ноутбук сохраняет поток, восстанавливает угол, выполняет анализ и расчёт коррекции.

Контроллер не вычисляет «готовые граммы», не выводит FFT вместо сырых данных, не скрывает пропуски интерполяцией и не управляет дрелью в этой версии. `STOP` в протоколе останавливает сбор данных; это **не физическая остановка привода**.

Предпочтение разработки: C и Zephyr/Nordic nRF Connect SDK с доступом к необходимым Nordic peripherals. Точная версия, поддержка board definition, USB stack, nrfx и карта памяти фиксируются в G01. Их совместимость с имеющимся загрузчиком ещё не проверена. Не смешивать драйвер RTOS и прямую настройку одной периферии без единственного явно назначенного владельца.

## 2. Договорённости до первой прошивки

G01 должен сохранить:

- Версии компилятора, SDK/Zephyr/NCS и зависимостей; воспроизводимый manifest/lock.
- Board target и overlay, привязанные к паспорту G00; действительные GPIO и полярность VCC.
- Карту Flash приложения, загрузчика, настроек загрузчика и возможных служебных областей.
- Поддерживаемый тип образа, сведения существующего загрузчика и метод проверки образа до загрузки.
- Путь восстановления, не требующий стирания загрузчика в обычной работе.
- Принадлежность SPIM, TIMER, GPIOTE, PPI, USBD, IRQ и резервирование ресурсов SDK.

До этого **нет достоверной универсальной команды прошивки**. Не применять `eraseall`, случайный board target или готовый UF2 от похожей платы. Первую загрузку выполнять в отдельном аппаратном срезе G01 после завершения G00 и проверок сборки/карты памяти G01. Полный G01 завершается уже после USB-проверки платы; круговой зависимости «сначала завершить G01, затем впервые прошить» нет. Текущая поставка разрешает документацию, но не загрузку аппаратуры.

## 3. Профиль первой полной записи

Идентификатор проектного профиля: `four-sensor-usb-v1`.

| ID | Устройство и место | Чтение | Режим |
|---:|---|---|---|
| 0 | BMI160, конец A | Acc XYZ + gyro XYZ, 12 байт | 800 Гц обе группы, Normal, ±2 g, ±250 °/с |
| 1 | LIS3DH, конец A | Acc XYZ, 6 байт | 1344 Гц, HR, ±2 g |
| 2 | BMI160, конец B | Acc XYZ + gyro XYZ, 12 байт | Как ID 0 |
| 3 | LIS3DH, конец B | Acc XYZ, 6 байт | Как ID 1 |

Каждый датчик имеет собственный счётчик физических событий и собственную линию DRDY. До RUNNING необходимо считать обратно все существенные регистры и сравнить с профилем. Начальные режимы без гироскопа/с одним датчиком допустимы в G03, но обязаны иметь другой конфигурационный хеш и явную маску каналов.

BMI160 допускает аппаратную синхронизацию своих accel/gyro, но конкретную последовательность включения, свежесть обеих групп и поведение выбранного DRDY нужно доказать G03/G04. Нельзя пометить старое ускорение и новую угловую скорость как одну одновременную запись. Если выбранный драйвер этого не обеспечивает, полный профиль не проходит приёмку; переход к отдельным событиям accel/gyro меняет профиль, поток и тесты, а не выполняется молча.

Для LIS3DH использовать согласованное многобайтное чтение с BDU и auto-increment. 12-битные HR значения знаково расширить после сдвига регистров на 4 бита; в пакет положить integer counts, не g. Для BMI передавать знаковые 16-битные counts. Сохранять локальные оси; геометрическое преобразование выполняется на ПК. Паспортные описания регистров: [ST LIS3DH](https://www.st.com/resource/en/datasheet/lis3dh.pdf), [Bosch BMI160](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmi160-ds000.pdf).

## 4. Ресурсы nRF52840

Предлагаемое распределение; G01 должен сверить его с выбранным SDK и ревизией SoC.

| Ресурс | Проектное использование | Ограничение |
|---|---|---|
| SPIM + EasyDMA | Один общий SPI, 4 CS | Один владелец, один transfer одновременно |
| GPIOTE | 6 независимых входных событий | 4 DRDY + зубья + индекс; ресурс SDK проверить |
| PPI | 6 маршрутов событие → capture | Не путать с DPPI других семейств |
| TIMER3 | 32 бита, 1 МГц, 6 CC для захватов | Все CC заняты; не использовать один из них для произвольного `now()` |
| TIMER4, резерв | При необходимости время без входных событий | Использование только после проверки сопоставления с TIMER3 |
| USBD | Native USB CDC | Фактическая скорость измеряется, не выводится из 12 Мбит/с USB |
| Watchdog | Контроль зависания обработчиков | Не скрывает причину перезапуска; новый session UUID |
| GPIO | 13 обязательных + optional debug | Конкретные площадки только после G00 |

TIMER3/TIMER4 имеют по 6 CC, младшие TIMER — по 4. SPIM умеет EasyDMA и назначение GPIO. Это аппаратные свойства, а не доказанная доступность ресурсов приложению с выбранным SDK. [Nordic Product Specification](https://docs.nordicsemi.com/r/bundle/ps_nrf52840/page/keyfeatures_html5.html), [таблица TIMER из Nordic PS](https://docs-be.nordicsemi.com/bundle/nRF52840_PS_v1.8/raw/resource/enus/nRF52840_PS_v1.8.pdf).

Перед реализацией проверить errata фактической ревизии. В частности, существуют errata GPIOTE о повторных событиях и USBD; драйвер/SDK должен применять соответствующие обходы. Не объявлять их автоматически применимыми всем платам. [Nordic revision 1 errata](https://docs.nordicsemi.com/r/bundle/errata_nrf52840_rev1).

## 5. Захват времени

Базовая схема: GPIOTE фиксирует выбранный фронт; PPI запускает `TASKS_CAPTURE[n]` общего TIMER3; ISR забирает уже захваченное значение. Время входа ISR и время завершения SPI не подменяют время DRDY. Захват по DRDY — время готовности результата фильтра, а не время исходного механического события до задержки фильтра.

Сопоставление CC:

| CC | Источник |
|---:|---|
| 0 | BMI_A DRDY |
| 1 | LIS_A DRDY |
| 2 | BMI_B DRDY |
| 3 | LIS_B DRDY |
| 4 | PHASE_TOOTH |
| 5 | PHASE_INDEX |

На старте каждого `time_epoch` TIMER3 начинается с нуля. Тик — 1 мкс, 32-битный wrap — `2^32 мкс = 4294,967296 с ≈71,58 мин`. Протокол передаёт 64-битное время.

Расширение до 64 бит должно учитывать:

1. По аппаратным захватам вести атомарный 64-битный anchor. Для очередного t32 использовать ближайшее значение по знаковой разности modulo 2^32 относительно младших 32 бит anchor.
2. Близкие события могут обслужиться не в хронологическом порядке. Полученное время записи может быть немного меньше anchor; anchor не уменьшать, запись сохранять с её временем. Сортировка всех датчиков по времени происходит на ПК.
3. Этот способ однозначен только когда расстояние до anchor меньше половины периода (`2^31 мкс`, около 35,79 мин). Во время RUNNING непрерывные DRDY обеспечивают существенно меньший интервал, но отказ всех входов обязан быть замечен.
4. После неопределённой долгой паузы, остановки таймера или потери непрерывности создавать новый `time_epoch`, отправлять CONFIG/GAP и не выдумывать число пропущенных оборотов таймера. Проверку длительности молчания можно вести монотонными часами ОС, не выдавая их за точное время измерения.
5. Для длительных IDLE-пауз предпочтительно начинать новый epoch при START. Любая смена epoch оформляется CONFIG до первых данных этого epoch. Между эпохами физическую непрерывность не предполагать.

Если проекту понадобится точное `now()` без событий, зарезервировать TIMER4/RTC и явно построить сопоставление. Возможный вариант — общий аппаратный START TIMER3/TIMER4 через PPI и отдельный CC TIMER4 для чтения. Его постоянный offset/дрейф и поведение на перезапуске нужно измерить; не считать два таймера автоматически одной шкалой. **Не читать время посредством capture в одном из шести занятых CC TIMER3.**

У каждого CC и GPIOTE события глубина хранения ограничена. Если второй фронт приходит до обслуживания первого, можно потерять событие, не зная точного количества. Флаг события не является счётчиком фронтов. Такая ситуация должна давать `unknown_loss`, а не придуманное число пропусков.

## 6. ISR, очередь событий и чтение датчика

ISR выполняет только ограниченную работу:

1. Считывает/подтверждает источник и capture по порядку, проверенному для выбранного SDK.
2. Присваивает наблюдаемому событию sequence и сохраняет capture, источник и флаги в ограниченную очередь.
3. При заполнении увеличивает счётчик потерь и агрегатор GAP; не ждёт освобождения.
4. Будит обработчик и завершается.

Запрещены в ISR: USB, printf/log-строки, JSON, динамическая память, ожидание SPI, ожидание mutex, повторные попытки без границы и вычисление FFT. Приоритеты задаёт G01 с учётом USB/RTOS; ISR не должен вызывать API, запрещённые для его приоритета.

Проектные пределы для G04/G05, которые ещё предстоит измерить:

| Величина | Цель / ограничение |
|---|---|
| Собственная длительность ISR | Цель ≤10 мкс; фактический максимум записать |
| Задержка обслуживания capture | Цель <50 мкс; превышение 100 мкс фиксировать как нарушение приёмки |
| Завершение чтения после DRDY | Цель ≤250 мкс; не позже 500 мкс в полном профиле |
| Блокировка прерываний | Не допускать ≥100 мкс; измерять под USB-нагрузкой |
| SPI timeout одного короткого чтения | 200 мкс, затем ошибка; уточнить по драйверу без скрытого увеличения |
| Автоматический перезапуск датчика | Максимум 1 на сеанс; затем FAULT до команды оператора |

Это проектные критерии, не характеристики проверенной прошивки. При их недостижении изменить реализацию или явно пересмотреть договорённость с новым расчётом, не переписывать результат измерения.

SPI worker обслуживает источники по очереди с контролем deadline и справедливости. Перед чтением проверить, что запись ещё относится к текущему поколению DRDY. После DMA проверить, не пришёл ли новый DRDY во время чтения. Если свежесть/атомарность нельзя гарантировать, запись не выдавать как годную: отметить потерю и причину. Нельзя соединять старую временную отметку с новым регистровым значением.

Для одновременных четырёх DRDY оценка чистого времени SPI на 4 МГц: два чтения по 13 байт и два по 7 байт =80 мкс. Адрес, CS, driver latency, проверка статуса и прерывания добавляются. Поэтому именно аппаратный тест решает, выполнены ли 250/500 мкс.

Повторное чтение регистра не восстанавливает потерянный образец. FIFO может стать отдельным режимом после доказательства соответствия samples ↔ DRDY ↔ sensor time. В базовом режиме не реконструировать отсутствующие timestamps по номинальному ODR и не выдавать FIFO-отсчёты как аппаратно захваченные. Любая такая реконструкция должна иметь отдельный флаг и профиль.

## 7. Очереди и память

Предлагаемое статическое распределение, проверяемое map-файлом и runtime high-water:

| Область | Бюджет |
|---|---:|
| Основное кольцо сериализованных данных TX | 64 КиБ |
| Capture event queue: 256 слотов по 32 байта | 8 КиБ |
| Резерв control/GAP и дедупликации команд | 8 КиБ |
| Сборка кадров, DMA buffers, временные структуры | 8 КиБ |
| Канонический CONFIG и проверка хеша | 8 КиБ |
| Стеки и постоянные структуры приложения | Цель ≤32 КиБ |
| USB/RTOS/драйверы | Измерить; предварительный резерв 64 КиБ |
| Свободный запас из 256 КиБ | Цель ≥32 КиБ после окончательного link/runtime анализа |

Сумма предварительных бюджетов — 192 КиБ; это оставляет 64 КиБ до физического объёма, часть которых может потребоваться toolchain/SDK. Требование свободного запаса ≥32 КиБ проверяется после всех фактических размещений. 64 КиБ — размер основной очереди, а не размер всей прошивки. BLE сюда не включён.

Для очередей применяется **drop newest**: не перезаписывать уже принятые записи. Sequence выдаётся до попытки постановки, поэтому пропуск виден. Счётчики точных потерь ведутся отдельно от ситуаций с неизвестным количеством. GAP имеет собственный ограниченный резерв; при исчерпании деталей ставится `GAP_DETAIL_LOST`, а накопленные totals продолжают расти.

При долгом отсутствии USB запись не продолжается бесконечно «без потерь». После 1 с непрерывного stall при заполненной очереди переходить в FAULT, прекратить принятие новых samples/edges, сохранить totals для STATUS и ждать восстановления связи. STOP/FAULT не стирают уже принятые буферы. Подключение USB не разрешает автоматически начинать новый механический опыт.

## 8. USB и расчёт потока

| Составляющая | Расчёт | Байтов/с |
|---|---|---:|
| Сырые регистры BMI | 2×800×12 | 19 200 |
| Сырые регистры LIS | 2×1344×6 | 16 128 |
| Всего содержимого регистров |  | 35 328 |
| Записи samples протокола | (2×800+2×1344)×28 | 120 064 |
| 60 PPR + index при 50 Гц | (3000+50)×16 | 48 800 |
| Samples + edges до обрамления |  | **168 864** |

Сборка смешанных samples в кадры и edges в отдельные кадры — до 4 мс ожидания или до заполнения payload. При двух кадрах каждые 4 мс и 44 байтах обрамления вместе с payload prefix получается около **190 864 байт/с**, без STATUS/CONFIG и с номинальными ODR. Это оценка, не жёсткий верхний предел при дроблении batches или отклонении часов.

Приёмка G05: устройство и приёмник выдерживают **250 000 байт/с полного закодированного потока** на протяжении не менее 30 минут в синтетическом тесте с корректным разбором/CRC/sequence; отдельный физический тест проверяет полный профиль и реальную частоту входов. Синтетический тест не доказывает свежесть датчиков. G13 расширяет испытание минимум до 90 минут и сценариев отказа.

USB CDC здесь использует native USB контроллера. Значение baud в терминале не равно физическому лимиту UART, но конкретный USB stack может использовать line coding/DTR для управления сеансом. Поведение необходимо определить и испытать. Нельзя делать вывод «115200 гарантирует только 11 КБ/с» для native USB; нельзя делать и обратный вывод «USB 12 Мбит/с гарантирует 1,5 МБ/с приложению».

USB worker не блокирует capture/SPI и не держит общие блокировки во время передачи. Любой partial write сохраняет неотправленный остаток кадра; следующему кадру запрещено вклиниваться внутрь него. Поток может разделить или объединить кадры произвольно; границы USB-пакетов протоколу не нужны.

## 9. Состояния и восстановление

```text
BOOT -> IDLE -> ARMED -> RUNNING -> DRAINING -> IDLE
  |       |       |        |          |
  +-------+-------+--------+----------+----> FAULT
FAULT -- исправление причины + явная команда --> IDLE
```

- BOOT: CS неактивны, периферия безопасно инициализируется, создаётся новый session UUID. Не включать двигатель; его управления здесь нет.
- IDLE: HELLO/CONFIG/STATUS доступны; изменение профиля допускается только здесь.
- ARMED: проверены регистры, границы ресурсов, USB и активные источники; до начала потока конфигурация подтверждена хостом.
- RUNNING: фиксированная конфигурация; timestamps и sequences сохраняются. Изменение диапазона/ODR/фильтра требует STOP и нового CONFIG.
- DRAINING: новые данные не принимаются; до 1 с на завершение очередей при исправном USB; затем END с указанием обрезки при необходимости.
- FAULT: причина и счётчики сохраняются; никакой бесконечной перезагрузки. Команда CLEAR_FAULT возвращает IDLE только после проверки, что причина устранена; при неустранённой причине остаётся FAULT. Recovery не продолжает прежнюю калибровку молча.

Ошибки питания/шины, неизвестная модель, несовпавшие настройки, насыщение, отсутствие DRDY, потеря индекса, переполнение, CRC команд и USB disconnect различаются. Насыщение — флаг записи и непригодность окна для коррекции; единичный saturated sample сам по себе не обязан сбрасывать всё устройство. Потеря фазовой опоры не прекращает автоматически сбор акселерометров, но делает фазовый анализ соответствующего окна непригодным.

Watchdog feeding допускается только после подтверждённого прогресса важных обработчиков, не из безусловного таймера. После reset новый UUID и причина перезапуска; хост завершает прежнюю запись как нештатную. Защищённость файла на ноутбуке — отдельный контракт хоста.

## 10. Проверки перед объявлением рабочего захвата

| Этап | Обязательное доказательство |
|---|---|
| G01 | Build manifest, memory map, проверенная совместимость образа/загрузчика; build без flash — отдельный результат |
| G03 | WHO_AM_I/CHIP_ID, readback, ODR, локальные оси, совместная свежесть BMI, сдвиг LIS HR |
