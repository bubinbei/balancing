# Как выполнять проект небольшими задачами

Этот порядок рассчитан на исполнителя с ограниченным контекстом. Подробности доступны по зависимостям; весь проект в каждый запрос не загружать.

## Один раунд

1. Взять текущую карточку из STATE; далее следовать зависимостям ROADMAP. P00 выполнен, `tools/check_project.py` доступен. По прямому запросу владельца между проверяемыми срезами продолжать автоматически; аппаратные блокировки не подменять pass и использовать независимые программные задачи.
2. Прочитать одну карточку и перечисленные в ней обязательные источники. Обычно достаточно 4–6 документов; не читать соседние проекты.
3. Сформулировать: результат этого раунда, что нельзя менять, какие файлы затрагиваются, чем подтвердить готовность.
4. Реализовать только этот результат. Если задача слишком большая, завершить явно названную часть, а всю карточку оставить незавершённой.
5. Запустить проверки карточки. Разделять `not_run`, `pass`, `fail`, `blocked`; отсутствие оборудования не превращает тест в pass.
6. Заполнить [отчёт](../templates/TASK_RESULT.md), обновить STATE и добавить новую запись в RECENT. Не стирать старые записи.
7. После P00 выполнить созданный там `python tools/check_project.py` и `git diff --check`; проверить индекс перед коммитом. В самом P00 сначала реализовать и проверить это средство.

## Статусы этапов

Источник статуса — YAML-поле `status` в каждой карточке; сводная таблица ROADMAP и текущая карточка STATE должны с ним совпадать. Возможны `planned`, `in_progress`, `blocked`, `passed`. Для `passed` нужны обезличенный отчёт `evidence/reports/<ID>.md` и фактические доказательства всей приёмки. Машинный реестр не обязателен: не создавать второй несогласованный источник правды.

Статус blocked описывает конкретно отсутствующий вход (например, нет платы для измерения VCC), а не сложность задачи. При частичном выполнении STATE должен называть уже сделанную часть и следующий проверяемый шаг.

Все предшественники этапа должны быть пройдены перед его аппаратной/финальной приёмкой. Подготовка независимой части документации/программ и математических тестов допустима раньше, но не даёт права пометить зависимый этап пройденным. Software pass и статус всей карточки фиксируются раздельно.

## Как писать следующий запрос

```text
Проект C:\work\balancing. Выполни один незавершённый срез текущей карточки из STATE.
Сначала: прочитай AGENTS.md, README.md, STATE.md и эту карточку.
Цель: <конкретный результат>.
Ограничения: <оборудование, данные и файлы, которые нельзя менять>.
Приёмка: <команды и физические проверки, если они разрешены>.
Нужные файлы: <карточка и 2–4 зависимости>.
В конце: отчёт, STATE/RECENT и проверки карточки; после P00 также check_project и diff --check.
Не переходи к следующей карточке автоматически.
```

Фраза «продолжи» внутри карточки означает продолжить её оставшуюся часть, а не перепроектировать весь стенд. При новой идее сначала проверить её влияние на принятый контракт.

## Доказательства

- **Источник:** паспорт производителя подтверждает возможность микросхемы, но не разводку купленного модуля.
- **Симуляция:** известная математическая модель проверяет алгоритм, но не реальный шум/фазу.
- **Сборка:** компиляция проверяет совместимость кода, но не распиновку и USB.
- **Настольное испытание:** подтверждает электронику в зафиксированных условиях, но не балансировку.
- **Роторное испытание:** требует отдельной механической готовности и подтверждает только исследованный диапазон.

Нельзя заменять отсутствующий реальный канал нулём без признака качества, дорисовывать пропущенные отсчёты как измеренные, объявлять синхронным чтение последовательных регистров или переносить старую калибровку без проверки совместимости.

## Что делать при неудаче

Сохранить исходный захват и конфигурацию. Сузить проблему до одного датчика/одного канала/одного участка времени. Сравнить ожидаемое и полученное значение с единицами. Исправлять одну причину за раунд. После изменения повторить затронутую приёмку, а не весь набор без причины.

Публикация описана отдельно в [PUBLISHING](PUBLISHING.md). Репозитории публичны: сырые данные и местные фотографии сначала остаются в игнорируемых папках.

## Когда возвращаться на аудит

Когда все критерии P00 и G00–G14 подтверждены, выполнить [AUDIT_HANDOFF](AUDIT_HANDOFF.md). Если критерий не достигнут, сохранить fail/blocked и конкретную границу: «карточка прочитана» не означает «этап пройден». Не подгонять статус ради вызова аудитора. Самопроверка исполнителя обязательна, но решение независимого аудита остаётся за следующей проверкой владельца.
