# Протокол сырых данных BLC1

Статус: **draft v1, planned**. Это конкретный контракт для реализации G02/G03; совместимых encoder/decoder и аппаратных записей пока нет. Изменение размеров, трактовки времени или алгоритма CRC после появления реализации требует новой версии или явно совместимого расширения.

Навигация: [начало](../README.md), [аппаратура](HARDWARE.md), [прошивка](FIRMWARE.md), [приёмка](VALIDATION.md), [G02](../tasks/G02-protocol-host.md), [G05](../tasks/G05-multisensor-usb.md), [G13](../tasks/G13-endurance-recovery.md).

## 1. Общие правила

- Все многобайтные целые — little-endian; знаковые — two's complement. Сериализовать по полям; `sizeof(C_struct)` и padding компилятора не являются форматом.
- Время — целые микросекунды общего контроллерного TIMER в пределах `time_epoch`, не Unix time и не время получения USB.
- `session_uuid` — 16 случайных байт на загрузку прошивки; одинаковый UUID после reset недопустим. В JSON — 32 lowercase hex без дефисов, на проводе — эти 16 байт в том же порядке.
- `frame_seq` — u32 modulo 2^32, отдельно для каждого направления USB. Устройство начинает с 0 при boot и сохраняет счётчик при переподключении USB. Хост начинает свой счётчик с 0 при новом открытии соединения; устройство не трактует это как новый измерительный сеанс. Присваивать до постановки в TX; потеря уже нумерованного кадра создаёт дыру.
- `sample_seq` — независимый u32 для каждого физического sensor_id; `event_seq` — независимый u32 каждого оптического input_id. Начало с0 при boot. STOP/START и новый CONFIG их не обнуляют. Не смешивать счётчики разных источников.
- Sequence обозначает наблюдённые события, а не обещанное физическое число измерений. Если hardware потерял фронты до ISR, количество может быть неизвестно; GAP/STATUS обязаны это сообщить.
- Один кадр не содержит несколько `time_epoch` или `config_revision`. Устройство запрещает смешивание старых данных и нового профиля внутри кадра.
- Native USB CDC — двунаправленный байтовый поток. Поток может дробиться в любом месте. Никаких строк логов, CSV или printf между бинарными кадрами.

## 2. Заголовок: ровно 24 байта

| Offset | Размер | Поле | Значение |
|---:|---:|---|---|
| 0 | 4 | magic | ASCII `BLC1`, байты `42 4C 43 31` |
| 4 | 1 | version | 1 |
| 5 | 1 | type | Таблица типов ниже |
| 6 | 2 | flags | В v1 только бит0 `SIMULATED`; остальные0 |
| 8 | 2 | payload_len | 0…1024 |
| 10 | 2 | reserved | 0 |
| 12 | 4 | frame_seq | Счётчик направления |
| 16 | 8 | t_base_us | Для data — минимум timestamps в кадре; для control — последнее достоверное время эпохи |

После заголовка идут `payload_len` байт payload и **4 байта CRC**. Максимальный размер кадра — **1052 байта**. `t_base_us` не превращает абсолютные timestamps записей в относительные и не заменяет `time_epoch` payload.

В IDLE допускается последнее захваченное время в `t_base_us`; оно может не продвигаться. Значение0 допустимо до старта эпохи. Не выдавать приблизительное время ОС за точный TIMER timestamp. HELLO содержит текущий `time_epoch`; сами данные всегда несут его в prefix.

### CRC

CRC-32/ISO-HDLC, также называемый IEEE CRC32: polynomial `0x04C11DB7`, reflected implementation `0xEDB88320`, init `0xFFFFFFFF`, refin/refout=true, xorout `0xFFFFFFFF`. CRC считается по **24 байтам заголовка и payload**, без самого CRC; результат записывается u32 little-endian.

Контрольные значения: ASCII `123456789` → `0xCBF43926`; пустая последовательность → `0x00000000`. Для Python результат должен совпадать с `zlib.crc32(bytes) & 0xFFFFFFFF`. CRC проверяет случайное повреждение, а не подлинность данных.

## 3. Типы кадров

| Type | Имя | Направление | Payload |
|---:|---|---|---|
| 1 | HELLO | Устройство → ПК | Ограниченный JSON |
| 2 | CONFIG | Устройство → ПК | Чанки канонического JSON с SHA256 |
| 3 | SAMPLES | Устройство → ПК | Prefix16 + N×sample28 |
| 4 | EDGES | Устройство → ПК | Prefix16 + N×edge16 |
| 5 | STATUS | Устройство → ПК | Фиксированный prefix + таблицы + counters |
| 6 | GAP | Устройство → ПК | 40 байт |
| 7 | END | Устройство → ПК | 48 байт |
| 128 | COMMAND | ПК → устройство | Prefix32 + ограниченный JSON |
| 129 | ACK | Устройство → ПК | Prefix32 + ограниченный JSON |

Неизвестный тип с корректным CRC можно сохранить как неизвестный кадр и пропустить по длине; нельзя интерпретировать его как samples. Неизвестная версия, ненулевой reserved или неизвестные flags — несовместимость, никакого автоматического START. Бит SIMULATED допускается только в синтетическом режиме; смешивание реальных и синтетических данных внутри одного сеанса запрещено.

## 4. HELLO и идентичность сеанса

Payload — UTF-8 JSON, не более1024 байт. Обязательные ключи:

| Ключ | Тип / правило |
|---|---|
| `session_uuid` | 32 hex |
| `protocol` | integer1 |
| `firmware_git` | ASCII commit ID сборки или `unknown` для явно немаркированной разработки |
| `firmware_build_id` | SHA256 канонического build manifest, 64 hex; manifest содержит commit/версии/параметры, но не этот хеш и не хеш итогового бинарника |
| `board_id` | ASCII модель/ревизия из G00; не серийный номер |
| `boot_reason` | ASCII enum: power_on/reset/watchdog/fault/unknown |
| `time_epoch` | u32 текущей эпохи |
| `config_revision` | u32 текущей конфигурации |
| `config_sha256` | 64 hex полного CONFIG |
| `max_payload` | 1024 |
| `timestamp_tick_ns` | 1000 |
| `simulated` | boolean |
| `next_request_id` | u32 следующей ещё не использованной изменяющей команды; начальное значение 1 |

В G01 сохраняется build manifest по тем же правилам канонического JSON, что CONFIG, затем его SHA256 внедряется как `firmware_build_id`. После сборки отдельный host manifest сохраняет SHA256 полного бинарника. Таким образом, нет циклического требования включить в бинарник его собственный хеш. До G01 поле допускает `unknown`; приёмка G14 этого не принимает. Идентификатор сборки не доказывает, что конкретная плата уже прошла аппаратные испытания.

HELLO отправляется при готовности USB, по запросу и после reset. Host обязан дождаться полного CONFIG и проверить его хеш перед START. Новое подключение USB не создаёт новый UUID само по себе; reset устройства создаёт.

## 5. CONFIG: версия условий измерения

Полный CONFIG — канонический JSON, максимум 8192 байта. Правила канонизации проекта: ASCII-ключи, сортировка ключей лексикографически, без пробелов между токенами, Unicode вне ASCII экранируется `\uXXXX` с lowercase hex; символы вне BMP — стандартной парой surrogate escapes. Допустимы только null/bool/int/string/list/object; floating point, NaN и Infinity запрещены. Целые записываются десятичными цифрами без ведущего `+`, лишних нулей и формы `-0`. Числа с дробью представлять парой целых `numerator/denominator` или масштабированными integers, знаменатель положительный. Дубликаты ключей запрещены. Эти правила должны иметь golden-тесты; не считать их полной реализацией RFC8785.

SHA256 считается по точным каноническим байтам. `config_revision` и `time_epoch` находятся в оболочке; если epoch меняется при том же профиле, хеш может остаться прежним. Revision увеличивается при изменении условий профиля; epoch увеличивается при изменении шкалы времени. Обе величины не обнуляются до нового session UUID. Завершение диапазона u32 требует нового сеанса, не молчаливого wrap.

Prefix каждого CONFIG-кадра:

| Offset | Размер | Поле |
|---:|---:|---|
| 0 | 4 | config_revision |
| 4 | 4 | time_epoch |
| 8 | 4 | total_json_len, 1…8192 |
| 12 | 4 | chunk_offset |
| 16 | 2 | chunk_len, 1…968 |
| 18 | 2 | flags: бит0 FIRST, бит1 LAST |
| 20 | 4 | reserved=0 |
| 24 | 32 | config_sha256, raw bytes |
| 56 | chunk_len | Фрагмент JSON |

`payload_len =56+chunk_len`. Чанки одной конфигурации идут последовательно без пересечения; FIRST имеет offset0, LAST заканчивается ровно на total_json_len. Повтор допустим только если байты совпадают. Host держит не более одной незавершённой конфигурации, лимит8192 байта и timeout2 с; при ошибке запрашивает CONFIG заново. Данные неизвестной конфигурации сохраняются сырыми, но не поступают в расчёт коррекции.

Полный CONFIG должен содержать:

- `profile_id`, `schema=1`, `spi_hz`, `sensor_layout_revision`, `mounting_revision`, `mechanics_revision`, `drive_revision`.
- Для каждого sensor_id: model/chip_id, расположение, диапазоны, ODR рациональным числом, режим питания/фильтров, представление counts, маску каналов, readback значимых регистров и источник времени `hardware_drdy`.
- Масштабы каналов в рациональных физических единицах, локальные оси/их отображение на систему стенда, задержку фильтра: известное значение либо `unknown`; не подставлять ноль вместо неизвестного.
- Для оптических input_id: PPR, используемый фронт, index/tooth, знак вращения, угол нуля в масштабированных единицах, способ формирования фронта.
- Параметры захвата/очередей/timeout, роль USB, режим synthetic/physical, точную трактовку BMI accel+gyro в одном sample.

Имена обязательных контейнеров: `sensors` — массив до 4 объектов, `phase_inputs` — массив до 2 объектов, `capture` — объект параметров времени, `queues` — объект лимитов, `transport` — строка `usb_cdc`, `simulated` — boolean. В объекте датчика использовать `id`, `model`, `chip_id`, `location` (`A`/`B`), `channel_mask`, `odr_hz`, `acc_range_g`, `gyro_range_dps` (null для LIS), `power_mode`, `filters`, `counts_format`, `scale`, `axis_map`, `register_readback`, `timestamp_source`, `filter_delay_us`. `odr_hz` и `scale` содержат явно именованные группы accel/gyro и рациональные значения; не объединять разные диапазоны одним безымянным коэффициентом. `counts_format` — `bmi_i16` или `lis_hr_i12_sign_extended`. Неизвестные физические параметры остаются null/`unknown` и блокируют зависящую от них приёмку.

Объект фазы содержит `id`, `role` (`tooth`/`index`), `ppr`, `edge` (`rising`/`falling`), `rotation_sign`, `zero_angle_udeg`, `conditioning_revision`. `capture` содержит `timer_tick_ns=1000`, `timestamp_source=hardware_drdy`, `epoch_policy=new_on_start`, `spi_timeout_us=200`. `queues` содержит `tx_bytes=65536`, `capture_slots=256`, `gap_slots=32`, `policy=drop_newest`. Прочие детали вложенных объектов дополняются в G02 как версия schema, с golden-векторами, до появления первого совместимого потока. Не считать отсутствие дополнительного поля равным нулевой задержке или отсутствию потерь.

Текстовый пример допустимых полей не является паспортом реально подключённых модулей. При изменении крепления/опор/привода обновляется соответствующая версия, даже если регистры датчиков не изменились.

## 6. SAMPLES

Общий prefix16:

| Offset | Размер | Поле |
|---:|---:|---|
| 0 | 4 | config_revision |
| 4 | 4 | time_epoch |
| 8 | 2 | count, 1…36 |
| 10 | 2 | record_size=28 |
| 12 | 4 | reserved=0 |

`payload_len =16+count×28`, максимум1024. После prefix идут записи ровно28 байт:

| Offset записи | Размер | Поле |
|---:|---:|---|
| 0 | 1 | sensor_id:0 BMI_A,1 LIS_A,2 BMI_B,3 LIS_B |
| 1 | 1 | channel_mask: биты0…5 AccX,AccY,AccZ,GyroX,GyroY,GyroZ |
| 2 | 2 | quality |
| 4 | 4 | sample_seq |
| 8 | 8 | t_capture_us аппаратного DRDY |
| 16 | 2 | AccX i16 |
| 18 | 2 | AccY i16 |
| 20 | 2 | AccZ i16 |
| 22 | 2 | GyroX i16 |
| 24 | 2 | GyroY i16 |
| 26 | 2 | GyroZ i16 |

LIS имеет mask7, gyro-поля обязаны быть нулевыми и не означают измеренную нулевую угловую скорость. BMI полного профиля имеет mask63. Непередаваемые каналы всегда0. В одном кадре можно смешивать разные sensor_id одного CONFIG/epoch. Порядок внутри каждого sensor_id соответствует sequence; глобальный порядок разных датчиков по времени не гарантируется.

Quality, один бит = наличие состояния:

| Бит | Значение |
|---:|---|
| 0 | SATURATED: хотя бы один активный канал у границы диапазона |
| 1 | TIME_UNCERTAIN: связь с capture не подтверждена |
| 2 | FRESHNESS_UNCERTAIN: свежесть одной/нескольких групп не доказана |
| 3 | LOSS_BEFORE: перед этой записью был GAP этого источника |
| 4 | SENSOR_RESTARTED: первая запись после перезапуска/нового режима |
| 5 | TIMESTAMP_RECONSTRUCTED: timestamp восстановлен, не прямой capture; базовый профиль не допускает |
| 6…15 | Reserved=0 |

Quality0 означает лишь отсутствие обнаруженных флагов. Это не свидетельство абсолютной точности. Для расчёта коррекции исключать записи с битами0,1,2,5 и окна, пересекающие GAP/смену режима. Нельзя заменить отсутствующую запись предыдущей с quality0. SPI timeout без полученных данных создаёт GAP, а не sample из нулей.

## 7. EDGES

Prefix16 как SAMPLES, но `count=1…63`, `record_size=16`. `payload_len=16+count×16`.

| Offset записи | Размер | Поле |
|---:|---:|---|
| 0 | 8 | t_capture_us |
| 8 | 4 | event_seq |
| 12 | 2 | flags |
| 14 | 1 | input_id:0 tooth,1 index |
| 15 | 1 | level:0 falling,1 rising; значение после фронта |

Flags: бит0 REJECTED_BOUNCE, бит1 TOO_FAST, бит2 TIME_UNCERTAIN, бит3 LOSS_BEFORE, бит4 GAP_DETAIL_LOST; остальные0. Отбракованный цифровой фронт можно сохранить с флагом для диагностики; он не увеличивает физический номер оборота в анализе. `event_seq` всё равно увеличивается для каждого наблюдённого входного события, включая отбракованное.

Нормальный профиль фиксирует один выбранный фронт на метку. Запись обоих фронтов требует другого CONFIG и двойного расчёта нагрузки. Фронт индекса сам по себе не задаёт знак вращения и не доказывает отсутствие пропущенных зубьев.

## 8. STATUS

Период —1 с в нормальном режиме и при существенной ошибке, но не более10 STATUS/с. Payload:

| Offset | Размер | Поле |
|---:|---:|---|
| 0 | 4 | config_revision |
| 4 | 4 | time_epoch |
| 8 | 2 | state:0 BOOT,1 IDLE,2 ARMED,3 RUNNING,4 DRAINING,5 FAULT |
| 10 | 2 | health_flags |
| 12 | 2 | sensor_count,0…4 |
| 14 | 2 | input_count,0…2 |
| 16 | 4 | tx_bytes_used |
| 20 | 4 | tx_bytes_high_water |
| 24 | 2 | capture_slots_used |
| 26 | 2 | capture_slots_high_water |
| 28 | 4 | current_usb_stall_ms |

Далее sensor_count записей по48 байт:

| Offset записи | Размер | Поле |
|---:|---:|---|
| 0 | 1 | sensor_id |
| 1 | 1 | channel_mask |
| 2 | 2 | flags: бит0 unknown_loss_seen, бит1 unavailable |
| 4 | 4 | last_sample_seq;0 если событий ещё нет, с unavailable/no-events через totals |
| 8 | 8 | observed_drdy_total |
| 16 | 8 | valid_reads_total |
| 24 | 8 | known_dropped_samples_total |
| 32 | 8 | unknown_loss_events_total |
| 40 | 4 | fifo_overrun_total |
| 44 | 4 | last_spi_error_code,0=no error |

Затем input_count записей по32 байта:

| Offset записи | Размер | Поле |
|---:|---:|---|
| 0 | 1 | input_id |
| 1 | 1 | configured_edge,0 falling/1 rising |
| 2 | 2 | flags: бит0 unknown_loss_seen |
| 4 | 4 | last_event_seq |
| 8 | 8 | observed_events_total |
| 16 | 8 | known_dropped_events_total |
| 24 | 4 | unknown_loss_events_total |
| 28 | 4 | min_observed_interval_us;0 если ещё не определён |

Затем ровно8 counters u64 в порядке: `rx_crc_errors_total`, `tx_dropped_frames_total`, `spi_timeouts_total`, `capture_overrun_suspected_total`, `invalid_commands_total`, `usb_stall_events_total`, `missing_drdy_windows_total`, `time_epoch_resets_total`.

Полная длина =32+48×sensor_count+32×input_count+64; для четырёх датчиков и двух входов352 байта. Health flags: бит0 GAP_DETAIL_LOST,1 CLOCK_UNCERTAIN,2 SENSOR_FAULT,3 USB_STALL,4 CONFIG_MISMATCH; остальные0.

Totals монотонны в пределах session. u64 не оборачивать: при достижении предела FAULT; u32 диагностические totals насыщаются на `0xFFFFFFFF` с health SENSOR_FAULT, а не превращаются в0. Факт неизвестной потери никогда не включается в known_dropped как будто количество установлено.

## 9. GAP: видимая потеря

Ровно40 байт:

| Offset | Размер | Поле |
|---:|---:|---|
| 0 | 4 | config_revision |
| 4 | 4 | time_epoch |
| 8 | 1 | stream_kind:0 frame,1 sensor,2 edge,3 clock |
| 9 | 1 | source_id;255 для общей проблемы |
| 10 | 2 | reason |
| 12 | 4 | first_seq |
| 16 | 4 | count |
| 20 | 4 | flags |
| 24 | 8 | t_first_us |
| 32 | 8 | t_last_us |

Reasons:1 capture_queue_full,2 tx_queue_full,3 sensor_overwrite,4 spi_timeout,5 capture_overrun_suspected,6 usb_disconnect,7 time_discontinuity,8 sensor_restart,9 phase_invalid,10 gap_detail_lost.

Flags: бит0 COUNT_UNKNOWN,1 TIME_UNKNOWN,2 DETAIL_LOST. Для неизвестного количества count=`0xFFFFFFFF`, COUNT_UNKNOWN=1; first_seq — ближайший известный sequence после проблемы либо0 при отсутствии привязки. Неизвестное время — оба timestamps0 и TIME_UNKNOWN=1. Известный диапазон — count>0, <2^31, последовательный modulo u32.

Соседние потери одного источника/причины можно объединить. Несмежные диапазоны нельзя склеивать в точную якобы сплошную потерю. Предусмотреть32 слота GAP; при переполнении сохранить totals, выставить DETAIL_LOST и позднее передать GAP с неизвестным диапазоном. Потеря деталей GAP сама является видимой деградацией.

Drop нового data-кадра даёт известный frame GAP и, когда доступна информация, соответствующие sensor/edge GAP. Если не удалось сохранить детализацию, totals и unknown-gap остаются обязательными. Host дополнительно обнаруживает holes sequence; одинаковую потерю, описанную и GAP, и дырой, нельзя суммировать дважды.

## 10. COMMAND и ACK

Устройство исполняет только команды известного сеанса. Prefix COMMAND32:

| Offset | Размер | Поле |
|---:|---:|---|
| 0 | 16 | session_uuid |
| 16 | 4 | request_id |
| 20 | 4 | expected_config_revision |
| 24 | 2 | opcode |
| 26 | 2 | args_len,0…992 |
| 28 | 2 | flags=0 |
| 30 | 2 | reserved=0 |
| 32 | args_len | JSON args; при0 трактовать как пустой объект |

Opcodes:

| Код | Команда | Условия |
|---:|---|---|
| 1 | GET_HELLO | Допускает нулевой UUID до знакомства; нет побочного изменения |
| 2 | GET_CONFIG | Только актуальный UUID |
| 3 | SET_PROFILE | Только IDLE; разрешённый profile_id и параметры из whitelist |
| 4 | START | Только IDLE после проверок; args содержит принятый config_sha256 |
| 5 | STOP | RUNNING/ARMED/DRAINING; повтор безопасен; не останавливает двигатель |
| 6 | PING | Нет изменения измерительных условий |
| 7 | CLEAR_FAULT | Только FAULT; проверяет устранение причины, при успехе IDLE; запись автоматически не запускается |

START создаёт новый time_epoch, отправляет ACK с его номером, полный CONFIG этого epoch, затем начинает data. Если проверка ARMED не прошла, возвращает отказ и данные не запускает. CONFIG/ACK должны попасть в поток до первых данных. `expected_config_revision` строго проверяется для SET_PROFILE и START; для GET_HELLO, GET_CONFIG, PING, STOP и CLEAR_FAULT допускается 0 и поле не ограничивает выполнение. UUID обязателен для всех команд, кроме первоначального GET_HELLO. Профиль не меняется во время RUNNING. Запись произвольных регистров, flash и GPIO через протокол не предусмотрена.

ACK prefix32:

| Offset | Размер | Поле |
|---:|---:|---|
| 0 | 16 | session_uuid |
| 16 | 4 | request_id |
| 20 | 2 | opcode |
| 22 | 2 | status |
| 24 | 4 | config_revision |
| 28 | 2 | body_len,0…256 |
| 30 | 2 | reserved=0 |
| 32 | body_len | JSON body |

Status:0 OK,1 BAD_ARGS,2 WRONG_SESSION,3 STALE_CONFIG,4 WRONG_STATE,5 UNSUPPORTED,6 INTERNAL_ERROR,7 REQUEST_ID_REUSED. Ответ должен объяснять отказ коротким ASCII code и русским/английским текстом по необходимости. Для START body содержит `time_epoch`; для STOP — состояние DRAINING/IDLE.

Для изменяющих команд SET_PROFILE/START/STOP/CLEAR_FAULT request_id начинается с 1, строго возрастает и не оборачивается в пределах session. Хранить кэш последних 8 таких request_id с хешем команды и ответом; дополнительно хранить максимальный использованный ID. ACK body ограничен 256 байтами, чтобы кэш действительно помещался в выделенный бюджет. Повтор ID/байтов из кэша возвращает прежний ACK без повторного действия. Другие байты того же ID или более старый ID, уже вытесненный из кэша, отвергаются как REQUEST_ID_REUSED. Изменяющие команды потребляют ID и при отказе, чтобы поздний повтор не стал новым действием. Read-only команды используют request_id=0, не входят в этот кэш и не меняют next_request_id. После переподключения хост сначала узнаёт next_request_id из HELLO. Достигнув предела u32, не выполнять новые изменяющие команды до нового сеанса. Хост имеет не более одной незавершённой команды, сопоставляет ACK по UUID/request_id/opcode, делает максимум 3 повтора с timeout 1 с; дальнейшая неопределённость — ошибка сеанса. На перезагрузке новый UUID сбрасывает кэш.

JSON во всех управляющих кадрах: глубина≤8, строка≤256 символов, array≤32 элементов, без duplicate keys/NaN/Infinity. COMMAND args — объект. Неизвестные изменяющие параметры отвергать, а не игнорировать; необязательные HELLO-поля хост может пропускать. Разбор не должен выделять память по неподтверждённой длине USB-потока.

## 11. END и завершение

Ровно48 байт:

| Offset | Размер | Поле |
|---:|---:|---|
| 0 | 16 | session_uuid |
| 16 | 4 | config_revision |
| 20 | 4 | time_epoch |
| 24 | 4 | last_data_frame_seq; 0 если data не было, при этом обязателен флаг NO_DATA |
| 28 | 2 | reason:0 requested_stop,1 fault,2 host_stall,3 device_shutdown |
| 30 | 2 | flags |
| 32 | 8 | t_end_us, последнее достоверное время |
| 40 | 4 | pending_gap_count |
| 44 | 4 | reserved=0 |

Flags: бит0 ORDERLY,1 HAD_GAPS,2 DRAIN_TRUNCATED,3 TIME_UNCERTAIN,4 NO_DATA; остальные 0. NO_DATA снимает неоднозначность, когда валидный sequence равен 0 или `0xFFFFFFFF`. ORDERLY означает оформленное завершение, а не отсутствие потерь. До END передаются доступные data, GAP и итоговый STATUS. END не стирает память/файлы хоста. Если USB исчез до получения END, хост помечает запись как незавершённую; нельзя дописывать выдуманный END от имени устройства.

## 12. Сборка и порядок кадров

Для SAMPLES/EDGES отправлять batch при достижении максимального payload либо через4 мс после первой записи. Не формировать отдельный кадр для каждого sample в нормальном режиме. Control/GAP имеют ограниченный резерв, но сериализатор сохраняет порядок frame_seq: нельзя отправить более поздний control посередине уже отправляемого data-кадра.

Устройство может отбросить ещё не отправленный data-кадр при исчерпании очереди только с GAP/totals. Уже частично отправленный кадр дописывается целиком или соединение считается оборванным; не вклинивать в его середину magic нового кадра. Хост хранит исходные байты даже при плохом CRC, отдельно от извлечённых валидных records.

## 13. Разбор и восстановление на ПК

1. Искать четыре magic-байта в ограниченном входном буфере. Хранить последние3 байта при несовпадении для поиска через границу read.
2. Дождаться24 байт заголовка. Проверить version, reserved, flags и payload_len≤1024 до выделения payload.
3. Дождаться ровно24+payload_len+4 байт, проверить CRC.
4. При плохом CRC сдвинуть поиск на1 байт после начала кандидата, а не на заявленную длину: ложный header может находиться внутри мусора.
5. При правильном CRC проверить структуру конкретного payload, включая count/record_size/длину. Не доверять только CRC.
6. Обновить frame sequence, session/config/epoch и counters. Sequence wrap трактуется modulo u32; изменение UUID означает новый сеанс.
7. Data без известного CONFIG/epoch сохранять, но не интерпретировать физически. Не заполнять holes средними значениями в сыром архиве.
8. Буфер поиска ограничить16 КиБ. При превышении сбросить непригодный префикс, сохранить факт/число отброшенных байт в журнале хоста и продолжить поиск. Это ошибка транспорта, а не GAP от имени датчика.

Поток не гарантирует глобальную сортировку samples и edges по timestamps. Анализ группирует записи по session/epoch/config, проверяет sequences и сортирует в ограниченных окнах с учётом максимального batch latency. Не начинать анализ окна, пока не пришли необходимые соседние фазовые фронты.

## 14. Что обязано пройти G02 и G13

Golden-векторы: header24, sample28 с отрицательными i16, edge16, max-length1052, CRC по стандартным векторам и полным кадрам, round-trip всех типов. Проверять сериализацию независимо от native-endian и выравнивания C.

Негативные тесты: каждый возможный разрыв короткого кадра, несколько кадров одним read, мусор между кадрами, magic внутри payload, плохая длина/CRC/count, неизвестные type/version, переполнение CONFIG, duplicate JSON keys, повтор/конфликт request_id, stale config, новый UUID, sequence wrap, time_epoch reset, hardware unknown-loss, GAP detail overflow, частичный последний кадр и отсутствие END.

Нагрузочные тесты: конечная память decoder при бесконечном мусоре, конечное число retries, 250 КБ/с закодированного синтетического потока, disconnect в середине кадра, длительный stall, ≥90 минут с настоящим rollover таймера при аппаратной приёмке. Чисто сгенерированный rollover подтверждает только decoder/арифметику.

Будущие отчёты: `evidence/reports/G02.md`, `evidence/reports/G05.md`, `evidence/reports/G13.md`. Обезличенные golden-векторы и результаты fault injection сохранять в `evidence/reports/G02/`, `evidence/reports/G05/`, `evidence/reports/G13/`. Эти файлы не созданы настоящим документом. Все аппаратные этапы остаются planned до фактической проверки.
